# Deploying to AWS (ap-south-1, Mumbai)

The exact steps to put the app on AWS. Read [architecture-and-costs.md](architecture-and-costs.md) first. **Every step that creates something on AWS needs the owner's approval before it is run.** Nothing in this repository deploys by itself.

Commands are for **Windows PowerShell**, run from the repository root unless noted. Values in `<angle brackets>` come from stack outputs (`aws cloudformation describe-stacks --stack-name <stack> --query "Stacks[0].Outputs" --profile nf-deploy`) or the console.

Never use root-account access keys, and never paste passwords or AWS secret keys into a chat, a ticket or a file in this repository.

## Order of work

| # | Step | Creates billable resources? |
|---|---|---|
| 1 | Account prerequisites | No |
| 2 | Sign-in and least-privilege deployment access | No |
| 3 | `cdk bootstrap` and the **Data** stack (database, secrets, storage, registry) | **Yes** (≈ $20/month: database, secrets) |
| 4 | Secrets (nothing to type: generated by AWS) | Included |
| 5 | Build the image, deploy the **Admin** stack, run the migrations | Minimal |
| 6 | Storage check | No |
| 7 | First admin, then operators in the app | No |
| 8 | Deploy the **App** stack (the website) | **Yes** (≈ $48/month more: Fargate, load balancer, IPv4) |
| 9 | Environment reference | — |
| 10 | Domain and HTTPS | Optional |
| 11 | Backup and recovery drill | Small, temporary |
| 12 | WhatsApp, only when authorised | Meta charges |

## 1. AWS account prerequisites

1. Use a company AWS account dedicated to this app (the budget alert covers the whole account).
2. Root user: strong password, **MFA on**, no access keys. Use it only for billing and account settings.
3. Billing: set the company's billing address and GSTIN under *Account → Tax settings* so invoices carry GST correctly. Turn on *Billing preferences → Receive billing alerts*.
4. On the office PC install: **AWS CLI v2**, **Node.js 24 LTS**, **Git**. Docker is **not** needed (images are built in AWS CodeBuild).

## 2. Sign-in and least-privilege access

1. Enable **IAM Identity Center** (AWS access portal) and create a user for each person who deploys. MFA required.
2. Create two permission sets:
   - `NfAdministrator`: AWS managed `AdministratorAccess`. Used **once** for `cdk bootstrap` and for rare account tasks; give it to as few people as possible.
   - `NfDeployer`: a custom permission set with the inline policy [`iam-deployer-policy.json`](iam-deployer-policy.json) (replace `ACCOUNT_ID` with the 12-digit account id). It can only deploy through the CDK roles, upload the build source, start the image build, run the admin task, and read the app's logs.
3. On the PC, create the CLI profiles (opens a browser to sign in; no keys are stored):
   ```powershell
   aws configure sso --profile nf-admin      # NfAdministrator, region ap-south-1
   aws configure sso --profile nf-deploy     # NfDeployer, region ap-south-1
   aws sso login --profile nf-deploy
   ```

## 3. Bootstrap CDK and create the Data stack

```powershell
cd infra
npm ci
npm test                      # 17 checks on the templates; must pass
$account = aws sts get-caller-identity --query Account --output text --profile nf-admin
npx cdk bootstrap "aws://$account/ap-south-1" --profile nf-admin     # once per account
```

Bootstrap creates a small staging bucket, an ECR repository and the `cdk-hnb659fds-*` roles that `NfDeployer` assumes. Optional hardening: pass `--cloudformation-execution-policies` with a policy narrower than `AdministratorAccess`.

```powershell
npx cdk deploy NfAttendance-Data --profile nf-deploy `
  --parameters NfAttendance-Data:AlertEmail=<it-alerts@yourcompany.in> `
  --parameters NfAttendance-Data:MonthlyBudgetUsd=90 `
  --parameters NfAttendance-Data:DatabaseMultiAz=false
```

Takes about 15 minutes (the database). Then **confirm the subscription email** AWS sends to the alert address, or alarms will not arrive.

Created: VPC (2 zones, no NAT gateway), security groups, RDS PostgreSQL 18 `nf-attendance-db` (db.t4g.micro, private, encrypted, TLS only, 7-day backups, deletion protection), secrets `nf-attendance/db-owner`, `nf-attendance/db-runtime`, `nf-attendance/app`, the private photo bucket, ECR repository `nf-attendance`, CodeBuild project `nf-attendance-image` with its source bucket, the monthly budget, the alert topic and two database alarms.

## 4. Secrets

Nothing to type. All three secrets are generated by AWS and are never shown to anyone:

| Secret | Holds | Read by |
|---|---|---|
| `nf-attendance/db-owner` | database owner (`nf_owner`) and password | the admin task only |
| `nf-attendance/db-runtime` | the app's database login (`nf_app`) and password | the web app, and the migration task (to create that login) |
| `nf-attendance/app` | `CRON_SECRET`; empty WhatsApp keys | the web app and the dispatch Lambda |

To rotate the app's database password later: generate a new value in Secrets Manager, run the migration task with `--runtime-role` (step 5) so PostgreSQL gets the same value, then redeploy the App stack.

## 5. Build the image, deploy the Admin stack, run the migrations

Images are built from **committed files only** (`git archive`), so `.env` files, `.data/` and worker masters can never reach AWS.

```powershell
cd ..                                              # repository root
git status                                         # must be clean: commit first
$tag = git rev-parse --short=12 HEAD
git archive --format=zip -o "$env:TEMP\nf-source.zip" HEAD
aws s3 cp "$env:TEMP\nf-source.zip" "s3://<BuildSourceBucketName>/source.zip" --profile nf-deploy
aws codebuild start-build --project-name nf-attendance-image `
  --environment-variables-override "name=IMAGE_TAG,value=$tag,type=PLAINTEXT" --profile nf-deploy
```

Wait until the build shows **Succeeded** (CodeBuild console, about 6–8 minutes). Tags are immutable: a commit is built once.

```powershell
cd infra
npx cdk deploy NfAttendance-Admin --exclusively --profile nf-deploy --parameters NfAttendance-Admin:ImageTag=$tag
```

**Before running migrations on a database that already holds data, take a manual snapshot** (§11).

Run the migration task. First without changes (it only prints the plan), then for real:

```powershell
$subnets = "<PublicSubnets>"          # e.g. subnet-0aa…,subnet-0bb…
$sg      = "<AppSecurityGroupId>"
$target  = "<MigrationTarget>"        # exactly as output: <db host>/nf_attendance
$net = "awsvpcConfiguration={subnets=[$subnets],securityGroups=[$sg],assignPublicIp=ENABLED}"

# 1) plan only
aws ecs run-task --cluster nf-attendance --task-definition nf-attendance-admin --launch-type FARGATE `
  --network-configuration $net --profile nf-deploy --query "tasks[0].taskArn" --output text
aws logs tail /nf-attendance/admin-tasks --since 10m --follow --profile nf-deploy   # Ctrl+C when it ends

# 2) apply, and create or update the app's database login (nf_app)
@{ containerOverrides = @(@{ name = "admin"; command = @("node", "scripts/db/migrate.mjs", "--apply", "--confirm-target", $target, "--runtime-role") }) } |
  ConvertTo-Json -Depth 5 | Set-Content -Encoding ascii "$env:TEMP\nf-migrate.json"
aws ecs run-task --cluster nf-attendance --task-definition nf-attendance-admin --launch-type FARGATE `
  --network-configuration $net --overrides "file://$env:TEMP\nf-migrate.json" --profile nf-deploy
aws logs tail /nf-attendance/admin-tasks --since 10m --follow --profile nf-deploy
```

Expect `Applied 13 file(s)` the first time and `Runtime login nf_app created`. A second run says `Pending: none`. The script refuses to run against any other target, refuses a changed migration that already ran, and rolls back a failing file completely.

## 6. Storage

Nothing to do: the photo bucket is private (all public access blocked, TLS only, versioned). The app gets 5-minute signed links. After step 8, upload a contractor photo in the app and check it shows; the object appears under `contractor-photos/` in the bucket. Excel masters are read in memory and never stored.

## 7. First admin and operator accounts

On the PC (the password is typed at a hidden prompt and never shown):

```powershell
npm run hash-password
```

Run the admin task with that hash. It is visible to people who can see task settings, so the app **forces a password change at the first sign-in**:

```powershell
@{ containerOverrides = @(@{ name = "admin"; command = @("node", "scripts/create-admin.mjs", "<admin@yourcompany.in>", "<Full Name>"); environment = @(@{ name = "ADMIN_PASSWORD_HASH"; value = "<hash from hash-password>" }) }) } |
  ConvertTo-Json -Depth 6 | Set-Content -Encoding ascii "$env:TEMP\nf-admin.json"
aws ecs run-task --cluster nf-attendance --task-definition nf-attendance-admin --launch-type FARGATE `
  --network-configuration $net --overrides "file://$env:TEMP\nf-admin.json" --profile nf-deploy
Remove-Item "$env:TEMP\nf-admin.json"
```

After step 8, sign in, choose your own password, then create plant operators in the app (**Plants → Plant attendance operators**) with temporary passwords and grant each one their plants. There is no self-registration.

## 8. Deploy the website (App stack)

```powershell
npx cdk deploy NfAttendance-App --exclusively --profile nf-deploy --parameters NfAttendance-App:ImageTag=$tag
```

The output **AppUrl** is the HTTPS address (`…ecs.ap-south-1.on.aws`). ECS Express Mode creates the load balancer, certificate, scaling (1–2 tasks) and a deployment alarm. A new task only receives traffic after `/api/health` (which checks the database) passes; a failing release rolls back by itself.

**Every later release**: commit → build the image (§5) → deploy Admin with the new tag → run the migration task (plan, then apply) → deploy App with the new tag.

**Rollback**: deploy App with the previous tag (`--parameters NfAttendance-App:ImageTag=<old tag>`). Migrations only move forward; if one must be undone, restore the snapshot taken before it (§11).

## 9. Environment reference

`.env.example` still describes the old Supabase setup and is not edited here (workspace rule). The current variables:

| Variable | demo | development | production (set by the App stack) |
|---|---|---|---|
| `APP_MODE` | `demo` | `development` | `production` |
| `DATABASE_URL` *or* `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD` | — | local database (`npm run dev:pg` sets it) | host/port/name as settings; user and password **from Secrets Manager** |
| `DATABASE_SSL` | — | `disable` (local only) | `verify-full` (required) |
| `DATABASE_SSL_CA` | — | — | `/app/certs/rds-global-bundle.pem` (in the image) |
| `DATABASE_POOL_MAX` | — | 1 with PGlite | 5 |
| `STORAGE_DRIVER`, `LOCAL_STORAGE_DIR` | — | `local`, `.data/uploads` | `s3` |
| `S3_BUCKET`, `AWS_REGION` | — | — | photo bucket, `ap-south-1` |
| `CRON_SECRET` | optional | optional | **Secrets Manager** |
| `WHATSAPP_LIVE_SENDING` | ignored | ignored (always simulated) | `disabled` (stack parameter) |
| `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN` | — | — | **Secrets Manager** (empty until approved) |
| `DEMO_SESSION_SECRET` | optional | — | — |

Admin scripts (migrations, first admin) use the database **owner** login instead: `MIGRATION_DATABASE_URL` or `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, plus `DB_RUNTIME_USER` and `DB_RUNTIME_PASSWORD` for `--runtime-role`. In AWS the Admin stack provides them from Secrets Manager.

## 10. Domain and HTTPS

- **From day one**: the AppUrl is HTTPS with a certificate AWS manages and renews. Cookies are `Secure` and HSTS is sent in production.
- **Own domain (optional, later)**: Express Mode has no CloudFormation setting for this. Request an ACM certificate for e.g. `attendance.<company domain>` (DNS validation), add it to the Express Mode load balancer's HTTPS listener with a host-header rule to the same target group, and point a DNS CNAME at the load balancer. Done in the console, this sits outside the stacks; if that matters, move the web stack to a standard Fargate service with its own load balancer.

## 11. Backup and recovery

- Automatic: daily backups kept 7 days with point-in-time restore (to within about 5 minutes), deletion protection, final snapshot on removal, versioned photos (old versions kept 90 days).
- Before every migration on a database with real data:
  ```powershell
  aws rds create-db-snapshot --db-instance-identifier nf-attendance-db --db-snapshot-identifier "nf-before-$tag" --profile nf-admin
  ```
- **Restore drill (do once after go-live, then every 6 months)**: restore a point in time to a *new* instance, check it, then delete the copy:
  ```powershell
  aws rds restore-db-instance-to-point-in-time --source-db-instance-identifier nf-attendance-db `
    --target-db-instance-identifier nf-attendance-db-drill --use-latest-restorable-time `
    --db-subnet-group-name <subnet group of nf-attendance-db> --vpc-security-group-ids <its security group> `
    --no-publicly-accessible --profile nf-admin
  ```
  Connect with a one-off admin task pointed at the copy (or check row counts in the RDS query editor), then delete `nf-attendance-db-drill` (it costs about $0.02/hour while it exists).
- A real restore: restore to a new instance as above, run a planned migration task against it, point the App stack at the new host (a short change in `infra/`), redeploy. Expect about an hour, plus the data entered since the restore point.
- Monthly Excel exports from the app are a useful offline record of attendance and payroll.

## 12. WhatsApp scheduling (only after written approval)

Live sending stays off until every item is done:

1. Meta WhatsApp Business account, a verified business phone number, and the two message templates approved under the names set in **Settings → WhatsApp** (`attendance_summary_hi`, `attendance_correction_hi` by default).
2. Worker consent recorded in the app for every number that will receive messages.
3. As `NfAdministrator`, put `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET` and a new random `WHATSAPP_VERIFY_TOKEN` into the `nf-attendance/app` secret (console, *Retrieve secret value → Edit*). Never put them in Git or chat.
4. In Meta's developer console set the webhook to `https://<AppUrl>/api/whatsapp/webhook` with that verify token.
5. Deploy the App stack with `WhatsAppLiveSending=enabled` and `WhatsAppScheduleState=ENABLED`.
6. In the app: set a test number, send to it only, then turn messaging on.

Delivery is **at most once** per logical notification: if the network fails after Meta accepted a message and before it was recorded, the message is marked *failed – check before retrying* and a person decides. Turning the schedule off again: redeploy with `WhatsAppScheduleState=DISABLED`.

## Removing everything

Delete stacks in the reverse order: App, Admin, then Data. Data has termination protection and the database has deletion protection; both must be switched off deliberately. The photo bucket, image repository and a final database snapshot are **kept** and must be deleted by hand if really unwanted.
